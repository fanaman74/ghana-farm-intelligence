## Verdict

The engineering is real and the honesty machinery is mostly real: geodesic areas, polygon-masked area-weighted raster statistics, provenance on every section, stale-while-error caching, a rule engine whose weights and evidence are exposed, and a documentation set that is unusually candid. Ten rounds of remediation have closed the four original blockers and most of the highs, and the claims I could test (test counts, live providers, typecheck) all held.

What remains is the same *shape* of defect as before, in four places:

1. **The account model is not wired into the admin surface.** Any signed-in account — including one an administrator created with no privileges — can publish a GMet advisory, and that advisory becomes the **top recommended action, confidence "high"**, on every other user's farm. I demonstrated this end to end.
2. **The analysis cache still identifies a farm by its own boundary while analysing the union of its fields**, so splitting, editing or adding a field and pressing *Analyse* can return the previous, differently-shaped result for up to three hours. Demonstrated.
3. **Two "last mile" claims are still wrong**: the crop panel is headed "Top three by evidence" while the selected crop is force-promoted into it, and a partial CHIRPS window still produces a `confidence: high` drought warning.
4. **The client is the least finished layer.** The Weather tab throws inside the React error boundary whenever there is no analysis — including the ordinary "press Refresh while the Weather tab is open" — and several failure paths mislabel what happened ("you are offline" for any server error, "Could not change the crop" after the crop was changed, a previous farm's analysis rendered under the newly selected farm).

Also still open from the previous review and not mentioned in its status table: the pH prediction interval is a 0–5 cm interval attached to a 0–30 cm value (M7 below), the WorldCover cross-tile fix never reached the map-overlay path (H4), and one test assertion is still a tautology.

**Grade: B+** — up from B. Good enough to run as a single-user or single-trusted-team tool once the Weather-tab crash (F1) is fixed; not yet safe as a multi-account deployment, because one unprivileged account can put text into everyone else's advice.

## High

### H1. Any signed-in account can publish advisories, and they become everyone's top action

`backend/app/api/admin.py:24-31` · `backend/app/analysis.py:64-67` · `backend/app/engine/recommendations.py:468-487, 509-510`

```python
def require_admin(x_admin_token: str | None = Header(default=None)) -> None:
    if not settings.admin_token:
        # Local-first deployment without a token: read/write is allowed but this
        # is recorded in the audit metadata returned by /admin/info.
        return
```

The guard only knows about `GFI_ADMIN_TOKEN`. It has no notion of the account model that round 10 added twenty lines away in `api/auth.py`, whose `_require_admin()` correctly returns 403 for a non-administrator. So with accounts enabled and no admin token — the documented, normal accounts deployment — **every signed-in user is an administrator for advisories and market prices**.

Proven with a `TestClient`, accounts enabled, two accounts (`admin`, `farmer` where `farmer.is_admin == 0`):

```
P2 farmer login: 200 0
P2 non-admin POST /api/admin/advisories -> 201 {"id": "74e67d66..."}
P2 non-admin GET  /api/admin/stats      -> 200
P2 non-admin GET  /api/auth/users       -> 403     # the same user, correctly refused
```

The second half is the part that matters. `analysis.load_farm` selects advisories globally — no owner, no region, no crop, and **no `valid_from` test** (`analysis.py:65-66`) — and `build_recommendations` turns each one into a recommendation with `confidence: "high"` and `category: "official_advisory"`, which is not excluded from `top_actions` (only `category == "data"` is, `recommendations.py:509`). A probe with an advisory dated `valid_from: 2026-12-25` (three weeks in the future) and the body *"Ignore your soil test and apply urea at 5 bags per acre"* produced:

```
recommendation ids : ['advisory_injected', 'wapor_unavailable']
top_actions        : [('advisory_injected', 'Injected by a non-administrator', 'high')]
```

That is the single "next action" at the top of every other account's Overview.

**Fix (three small edits):** have `require_admin` consult `auth.current_user()` when `auth.accounts_enabled()` (and keep the token path for the no-accounts posture); filter advisories by `valid_from <= today`, and by `regions`/`crop_ids` when the advisory sets them; and mark advisory-derived recommendations so they cannot outrank field-evidence actions.

### H2. The analysis cache key ignores fields, so field edits return the previous field's analysis

`backend/app/analysis.py:562-581` (key) vs `backend/app/analysis.py:82-93` (what is analysed)

```python
geometry = farm["geometry"] if not field_id else next(
    (field["geometry"] for field in farm["fields"] if field["id"] == field_id), farm["geometry"]
)
```

`analysis_key` hashes the **farm's** boundary when `field_id is None`. But `farm_geometry(farm, None)` analyses the **union of the farm's fields** whenever any field exists (`analysis.py:88-92`). Neither the field ids, nor the field geometries, nor their count enters the key — and `_inputs_fingerprint` covers only soil tests and advisories.

Proven:

```
P1 farm-only key         : analysis:a57866731d03a5c047ecd2ee
P1 key with 1 field      : analysis:a57866731d03a5c047ecd2ee  same as farm-only: True
P1 key after field edit  : analysis:a57866731d03a5c047ecd2ee  same: True
P1 key after adding 2nd  : analysis:a57866731d03a5c047ecd2ee  same: True
```

`POST /api/farms/{id}/analysis` defaults to `force: false`, so within `GFI_ANALYSIS_CACHE_TTL` (3 h) the app returns a payload carrying the *old* `farm.geometry`, `area_ha`, `perimeter_m`, soil statistics, terrain statistics, rainfall windows and NDVI for a boundary that no longer exists. The payload's own `"geometry_label"` records the mismatch ("union of 2 fields") while describing one; nothing compares it with the farm as it is now. The split-into-fields feature is how a user reaches this state in normal use.

**Fix:** key on what is actually analysed — `stable_hash([farm_id, field_id, geometry_actually_used, sorted field ids, ...])`, where the geometry comes from `farm_geometry()`. Bump `ANALYSIS_VERSION` to abandon existing entries. Add the regression test the current suite is missing (it has one for soil tests, `test_core.py:668`, none for fields).

### H3. Field routes do not scope `field_id` to `farm_id`, and delete has no ownership check

`backend/app/api/farms.py:327-357`

`create_field` and `update_field` call `_farm_row(farm_id)`, which is the project's single ownership enforcement point (documented as such at `auth.py:41-43`). Then:

```python
conn.execute(f"UPDATE farm_fields SET {assignments} WHERE id=?", (..., field_id))   # :349
...
conn.execute("DELETE FROM farm_fields WHERE id=? AND farm_id=?", (field_id, farm_id))  # :356
```

- `update_field` never checks that `field_id` belongs to `farm_id`, so an account that owns *any* farm can rewrite the name, crop or geometry of a field on someone else's farm by passing its own farm id and the other field's id.
- `delete_field` skips `_farm_row` entirely, so it does not even require ownership of a farm — only a valid session.

Exploitation needs a field id (32 hex characters, not enumerable), so this is not a practical mass attack, but it is exactly the isolation the account feature claims, and it is the only farm-mutating route that forgets the helper.

**Fix:** `WHERE id=? AND farm_id=?` on the update, and `_farm_row(farm_id)` at the top of `delete_field`; add an API test for the cross-tenant case (there is currently no test that touches fields at all).

### H4. The WorldCover cross-tile fix never reached the map overlay

`backend/app/geo/layer_render.py:312-320` vs `backend/app/providers/landcover.py:61-107`

The statistics path was correctly rebuilt to mosaic every intersecting 3°×3° tile (`landcover.py:76-107`, reported by `tiles: {requested, read}`). The overlay path still opens **one** tile:

```python
url = landcover_tile(centre_lat, centre_lon)
with open_raster(remote_cog(url), GDAL_HTTP_TIMEOUT="60") as dataset:
    rw = read_polygon(dataset, geom)
```

Ghana is cut by the 0° meridian and by 6°N and 9°N, so fields near Tema, Ho, Keta, Sunyani or anywhere along those lines span two tiles. `read_polygon` is called with `boundless=True`, so the part of the field outside the opened tile reads as nodata/0; class 0 is not in `CLASSES`, so those pixels are dropped and simply **not drawn** — the field appears half-covered, with no warning, while the Land-cover panel above it reports fractions computed over both tiles.

This directly contradicts `layer_render.py:1-6` ("Every layer is produced from the same polygon-masked rasters used for the statistics") and `docs/ARCHITECTURE.md:101-103` ("so the map and the panel cannot drift apart").

**Fix:** reuse the `merge`-based mosaic from `landcover.analyse` (extract it to a helper and call it from both), and attach the `classified_fraction` the statistics now report.

### H5. A partial CHIRPS window still produces a full-confidence drought warning

`backend/app/providers/chirps.py:395-431` → `backend/app/engine/recommendations.py:299-328`

The B4 fix is real at the provider layer: each window now carries `complete`, `days_covered`, `expected_days`, `missing[]`, per-month mode, and the climatology baseline is scaled to the covered days (`_baseline_total(..., days_covered=...)`). The anomaly label appends `(partial record: n of m days)`.

The recommendation does not read any of it:

```python
percent = month_anomaly.get("percent_of_normal")
if percent is not None and percent < 70:
    ...
    severity="warning" if percent < 50 else "watch",
    priority=1 if percent < 50 else 2,
    confidence="high",
```

So a window with ten of thirty days observed — or one where a single daily raster failed inside a month — still raises `priority=1, confidence="high"`, and the `why` text says *"The last 30 days of available CHIRPS data (ending …) recorded X mm, Y % of the … long-term average"*, when it is not 30 days. The scaled baseline makes the number roughly unbiased but does not make the statement true, and the whole point of the original blocker was that a provider gap must not read as a drought.

**Fix:** when `complete` is false, either suppress the recommendation or cap `confidence` to "medium" and put the covered-day count in `why` and in the evidence rows (the data to do this is already in the payload).

### H6. "Top three by evidence" contains a crop the engine did not rank in the top three

`backend/app/analysis.py:344-351` · `frontend/src/components/panels.tsx:1402-1408`

```python
if selected_eval["category"] != "insufficient_data" and selected_eval["id"] not in {
    item["id"] for item in ranking["ranking"]
}:
    ranking["ranking"] = [selected_eval] + ranking["ranking"][:2]
```

The panel then renders that list under the heading **"Top three by evidence"** (`panels.tsx:1403`) with no rank numbers and no marker, and the same crop is already shown in full in a `CropCard` immediately above (`panels.tsx:1401`). A farmer who grows cocoa on a field the engine scores as marginal sees "Top three by evidence: cocoa, …" at the top.

This is a small, deliberate-looking piece of UX (the user's crop should be visible), implemented in a way that makes the engine's own ranking false.

**Fix:** keep `ranking` as the engine's top three and render the selected crop separately with its real position ("Selected crop — ranked 7th of 20"); `rank_score` and `data_coverage` are already in each evaluation, so the honest label costs nothing.

## Medium

**M1. Soil "valid coverage" is the minimum over every property, so one unpredicted property reports 0 %.** `soilgrids.py:311-313` takes `min(valid_fraction)` across all nine properties, and that single number is used for the section's confidence (`suitability.py:262-263`), for the soil-test recommendation text ("only 0 % of the field had valid predicted cells", `recommendations.py:93`), and for the PDF. `cfvo` in particular is frequently "no prediction" (0 in the raster), so a field with complete pH/texture/SOC and no coarse-fragment prediction reports 0 % coverage and a low-confidence ranking. Use the properties guidance actually depends on (pH, SOC, clay/sand/silt) or report the median, and let the per-property values carry the rest.

**M2. The scouting recommendation has no minimum valid-pixel guard.** `sentinel2._spatial_pattern` (`:145-184`) is attached to the latest scene whenever `valid.any()` and `sd > 0`, and `recommendations.py:353` turns `low_vigour_share >= 0.25` into a `priority=1` "Inspect the north-east part of the field". A scene with four usable cloud-free pixels can trigger it; the section's own warning about a partly cloudy latest image does not travel with the recommendation. Require a valid fraction (or pixel count) before the pattern is produced and say so when it is refused.

**M3. Planting advice pairs month-old rainfall with today's forecast.** Measured today: `latest_available` for CHIRPS is **2026-09-30**, i.e. a **33-day** lag. The rule sums the last 14 *available* days (ending 30 Sep) and the next 5 forecast days, then says "Plant in the next few days if your seedbed is ready". The evidence rows do say "last 14 available days" and "Historical daily data through 2026-09-30", which is the honest version of B2 — but the decision itself still mixes a 33-day-old observation with a live forecast. Refuse the planting rules (or downgrade to a "watch" with the lag in the title) when `lag_days` exceeds ~21.

**M4. `accounts_enabled()` is a process global, so `uvicorn --workers N` silently disables authentication.** `auth.py:47,92-101` caches a boolean, set at startup and refreshed on account create/delete — in the process that made the change. A worker started before the first account existed keeps `False` forever and serves the private API unauthenticated. `docs/LIMITATIONS.md:56` says "one replica" but says nothing about workers, and the Docker CMD is single-worker today. Either query the `users` table (one `COUNT(*)` on a tiny table, per request) or revalidate on a short TTL, and document that `--workers` is unsupported.

**M5. `/api/health` misreports the auth posture when accounts are enabled.** `core.py:43-51` reports `farm_data: "access_token"` or `"open"` and never `"accounts"`, so an accounts deployment says "open" while every farm route returns 401. This field is asserted in CI (`ci.yml:94`) and quoted in the docs as the deployment's posture.

**M6. No rate limit or lockout on `/api/auth/login`.** `api/auth.py:61-82` verifies PBKDF2-200k per attempt with no delay, no per-IP counter and no account lockout; only the username-enumeration protection is in place. Combined with `GFI_COOKIE_SECURE` defaulting to `False` (`config.py:143`), a public accounts deployment is brute-forceable and can leak its session cookie on plain HTTP. At minimum, add a small in-process failure counter and make `cookie_secure` default to true when `GFI_ENV=production`.

**M7. The pH prediction interval is a 0–5 cm interval attached to a 0–30 cm value (carried over, still open).** `recommendations.py:75` reads `uncertainty.phh2o.depths["0-5cm"]`; `:74` reads `profile_0_30.phh2o.value`, a depth-weighted 0–30 cm mean (`soilgrids.py:239-259`). The card's `why` then says *"Estimated topsoil pH is 5.0 … 90% prediction interval pH 4.6–5.5"* and the evidence row is labelled **"Topsoil pH (0–30 cm)"**, so the quoted value can fall outside its own quoted interval. Either compute a 0–30 cm interval (all three depths are already fetched) or label the row 0–5 cm and stop mixing.

**M8. Concurrency is still unbounded per analysis.** `_EXECUTOR` runs `job_workers` (3) jobs; each `build_analysis` opens its own 4-thread pool (`analysis.py:261`); soilgrids opens 4 (`:203`); CHIRPS opens 10, 3, 10 and 6 in different places (`chirps.py:211,350,356,444`), plus WaPOR's probe. Worst case is dozens of concurrent HTTPS/COG reads from one process with no global cap, on a SQLite-backed worker pool. A single provider slow-down multiplies across all of them. A shared `BoundedSemaphore` around provider I/O would make the resource ceiling a number you chose.

**M9. Progress emits still build the whole partial payload.** `analysis.py:244-253:247` — round 4 fixed the *storage* cost by storing only per-section statuses, but `emit()` still calls `_partial_payload()` first, which serialises every section (`json_safe` recursion over Sentinel-2 history, corners, legends, monthly series) at each of eight steps, and `_progress_summary` then throws nearly all of it away. Build the summary directly from `sections`.

**M10. Two different 422 bodies for the same failure.** `create_field` (`farms.py:294-296`) raises `HTTPException(422, detail={code, message, detail})`; `update_field` (`farms.py:336`) lets the app-level `GeometryError` handler answer with `{"valid": false, "error": {...}}` (`main.py:178-180`). A client that reads `detail` shows nothing useful for a failed field-geometry edit.

**M11. Advisories are not scoped to the farm's region or crop, nor to `valid_from`.** Separate from H1 and true even with a trustworthy administrator: `analysis.py:64-67` filters on `valid_to` only, although `advisories` stores `regions` and `crop_ids` and `/api/admin/advisories?region=` already filters on region. The Bono farmer sees a Volta bulletin, and a bulletin dated for next month is shown now.

## Frontend

`App.tsx` (1,471 lines), `panels.tsx` (2,601), `MapView.tsx` (1,044), `api.ts`, `ui.tsx`, `offline.ts` and `vite.config.ts` were read in full in a parallel pass; every finding below was checked against the source, and I re-verified the top four myself. ### F1. Blocker — the Weather tab crashes the app whenever there is no analysis

`panels.tsx:1017-1027`, reachable from `panels.tsx:513` and `App.tsx:499`

```jsx
{useSectionBody(section, (
  <>
    ...
    <StatusChip status={section!.status} />
```

The JSX argument is evaluated *before* `useSectionBody` can decide whether to render it, so `section!.status` dereferences `undefined` — `!` is erased at compile time. `section` is `undefined` before the first analysis, and again on **every refresh**, because `runAnalysis` calls `setAnalysis(null)` and re-fetches. So: open the Weather tab, press Refresh → `TypeError` → the root `ErrorBoundary` (`main.tsx:51`) replaces the whole app with "Something went wrong in this view" until reload. The other three `useSectionBody` call sites (`:763`, `:1447`, `:1650`) pass only literals and are fine.

**Fix:** `section?.status ?? "unavailable"`, and add a smoke test that renders each tab with `analysis = null` — the Playwright suite never opens Weather on an empty panel.

### F2. High — an analysis can be rendered under the wrong farm

`App.tsx:432-433, 458`

`selectFarm` clears the analysis but does not abort the previous run or bump `analysisRun`; that only happens inside `runAnalysis`, *after* `await api.getFarm(farmId)`. When that fetch fails (the offline path, which falls back to the cached farm list), `runAnalysis` never runs, farm A's in-flight poll completes, and `setAnalysis(current => current ?? saved.analysis)` keeps A's payload while `farm` is B — B's name and area over A's soil, NDVI and recommendations. Nothing compares `analysis.farm.id` with the selected id.

**Fix:** bump/abort in `selectFarm` before the fetch, and gate every `setAnalysis` on the payload's farm id.

### F3. High — a single-field analysis is accepted as the whole-farm analysis

`App.tsx:466-472` (vs the correct guard at `:457`), `backend/app/api/farms.py:605`, `backend/app/db.py:486`

The cached branch explicitly rejects a field-scoped payload (`field_id === null`), but the "latest job" branch has no such check, and `job_latest_for_farm` orders by `created_at` only. Analyse Field B (0.4 ha), then reopen the farm: the panel shows Field B's geometry, soil, weather, NDVI and actions under the farm's name and the farm's 12 ha area. The same endpoint feeds the PDF export, so a farm report can carry a field's analysis. This is the offline scope bug (M7 in the old review) surviving in a second code path.

### F4. High — a failed refresh destroys the analysis that was on screen

`App.tsx:496-500, 544-547`

`runAnalysis` blanks `analysis`, `partial` and `job` *before* the request, and the catch only toasts. The `[selectedFarmId]` effect does not re-run, so the panel falls back to "This farm has no analysis loaded…" and the NDVI/NDMI overlays disappear — while `offline.loadAnalysis` still holds the result. Any provider 5xx or a refresh while offline silently deletes the only visible copy of a computed analysis. Keep the previous value in a ref and restore it on failure.

### F5. High — every server error is reported as "you are offline, showing saved data"

`App.tsx:546-547` (and `:435`)

`setOnline(false)` runs for any thrown error, not just a transport failure: a 408 polling timeout, a 409, a 422, a provider-side 502. The banner then claims *"Offline — showing saved data from … Live updates need connectivity"* and the panel says "Saved on device", and the flag only clears on a later successful `getFarm`. That is a false provenance statement on the surface that exists to be honest about provenance. Test `error.status === 0` (the client's own no-connection code) and surface the real status otherwise.

### F6. High — the offline farm cache is global, not per account

`offline.ts:28-37`

One key `"all"` holds every farm, including boundaries, and analyses are keyed by farm id only. The app supports accounts and states that boundaries are private, but on a shared device `offline.loadFarms()` (`App.tsx:343-347`) loads and draws the previous account's farms whenever the list call fails. Sign-out does not clear them (`clearOffline` clears analyses only). Prefix the keys with the account id, or wipe the farm cache on sign-out.

### Medium (F7–F19)

- **F7. `stale` sections are rendered as fresh.** `useSectionBody` (`panels.tsx:50-62`) only special-cases `unavailable`/`error`, so a `stale` section (real: `soilgrids.py:336`, `openmeteo.py:266`) shows values with no marker and no retrieval date. Only Weather has a `StatusChip` (`panels.tsx:1027`); `SectionHeader`/`retrieved_at` (`ui.tsx:138-161`) is dead code. Render the header on every tab.
- **F8. Every source row says "Fetched unknown".** `ui.tsx:125` reads `source.fetched_at`, but `Source.as_dict()` (`providers/base.py:148-160`) has no such field — only the analysis-level `provenance` array adds it (`analysis.py:170`), and the frontend never reads `analysis.provenance`. The one "when was this fetched" field in the UI is `unknown` for every dataset on every tab.
- **F9. Two contradictory areas on one screen.** `panels.tsx:439` prints `farm.area_ha` (whole farm) while `:603` prints `analysis.farm.area_ha` (the selected field); `activeFieldId` never reaches the header, and the only clue is `field:Name` buried in a "Geometry" table row. Show `geometry_label` and use one source of truth.
- **F10. Split-into-fields is not atomic.** `App.tsx:752-766` issues N sequential `POST /fields` with no rollback and no refresh on failure: if part 3 fails the user is told "Could not split the boundary" while fields A and B exist server-side, and retrying duplicates them.
- **F11. Editing vertices deletes polygon holes.** `MapView.tsx:1006-1015` rebuilds a single-ring polygon; `beginEdit` guards `MultiPolygon` only, not `coordinates.length > 1`. A KML/GeoJSON import with a hole loses it on the next vertex drag, silently.
- **F12. Nulls become plausible zeros in charts, and measured zeros disappear.** `panels.tsx:1508` draws a zero-width NDVI bar for a null value (`—` printed beside it); `:1896` draws a 2 % minimum bar for a null rainfall day that is indistinguishable from a real 0 mm day; `:1114` renders an empty anomaly bar labelled "No baseline". GPS point spacing compares CSS pixels with a metres promise.** `MapView.tsx:726-732` uses `map.project` distances `> 8`, which is ~19 m at the forced zoom; `App.tsx:616` tells the user "more than 8 m". ## What is genuinely good (unchanged, and worth protecting)

1. **Geodesy** — `Geod.geometry_area_perimeter` on WGS84, equal-area centroid via EPSG:6933, self-intersection reported with `explain_validity`, honest minimum-area rejection.
2. **Raster statistics** — windowed reads, polygon rasterisation (not bbox averaging), geodesic per-row pixel areas, weighted quantiles, explicit `valid_fraction`, and the `sub_field_detail ≥ 4 px` rule that *tells* a user their field is smaller than a soil cell. The round-1 correction (statistics had been computed over the padded bbox window) was a real catch and is properly regression-tested.
3. **The `Section`/`Source` provenance model** — the single best idea in the codebase. It is why the remaining failures are visible at all.
4. **`providers/base.py` stale-while-error cache** — last good payload, labelled stale with its original timestamp. The right design, exercised by a test that could fail.
5. **The migration to real accounts** — PBKDF2 with per-account salt, session tokens stored as hashes, 404 rather than 403 for another account's farm, last-administrator guard, password change invalidating other sessions. The design is right; H1/H3 are integration gaps, not design failures.
6. **CI that runs the real artefact** — builds the image, boots it, asserts the posture, asserts PID 1 is not root, runs all 16 browser tests against the container. Most projects this size do not get near this.
7. **Documentation discipline** — `LIMITATIONS.md` names the WaPOR 502, the 33-day CHIRPS lag, the root-volume trade-off and the "not built in the authoring environment" gap. It tells a reviewer what to distrust.

## Suggested order of work

1. **F1** — one `?.` away from a crash-free Weather tab; add a "render every tab with no analysis" test so it stays fixed.
2. **H1** — one guard, one filter: gate `/api/admin/*` on the account flag, and scope advisories by `valid_from`/region/crop. It is the difference between "a team can share a deployment" and "the first user can poison the second user's advice".
3. **H2, H3, F2, F3** — identity and scoping: the analysis cache key, the field-route farm check, and the two client paths that let one farm's or field's analysis appear under another. Each is a handful of lines with a regression test.
